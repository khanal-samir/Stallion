# PRD: Sequence Automation With Gmail Autosend, AI Tasks, and Reply Detection

## Problem Statement

Sales teams using Stallion can manage people, organizations, deals, and dashboard activity, but they cannot yet run structured outbound sequences from the CRM. A user who wants to contact a person, wait a few days, send a follow-up, and create a LinkedIn/manual task must track that process manually outside the product.

The desired product is a CRM-native sequence workflow where users can design a sequence visually, enroll people, let Gmail send sequence emails on schedule, detect replies to stop the relevant enrollment, generate task copy with AI, and monitor work from the dashboard.

## Solution

Add a workspace-shared Sequences product area that lets users build linear Make.com-inspired outbound flows. MVP sequences support Email, Wait, LinkedIn Task, and General Task steps. Users connect Gmail separately from normal Google login, publish sequence versions, enroll existing CRM people, and choose the connected Gmail sender for each enrollment.

Email steps autosend through Gmail from a saved subject/body configured on the sequence step. Wait steps use calendar days and sending-window rules. LinkedIn and general task steps create dashboard tasks, with LinkedIn message text generated by Groq and editable by the user. A separate worker polls every minute, claims due work, enforces sending windows and per-account rate limits, handles retries, logs activity, and avoids live Gmail calls unless live sending is enabled.

Reply detection is included in MVP. The Gmail integration requests send and metadata access in the test environment. The worker tracks sent Gmail thread IDs and stops only the specific enrollment when a reply is detected in that thread. The product does not read reply bodies for MVP.

Every autosent email includes a public unsubscribe link. Unsubscribe confirmation happens on a Next.js page backed by API endpoints. Confirming an unsubscribe suppresses that recipient email address across the workspace and blocks future sequence emails.

## Implementation Decisions

- Add a workspace-shared sequence domain with drafts, published versions, step definitions, enrollments, enrollment steps, tasks, activity events, Gmail integrations, suppression records, and unsubscribe tokens.
- Sequence routes:
  - Sequences list
  - New sequence visual builder
  - Sequence detail with Builder, Enrollments, and Activity tabs
- Sequence builder is Make.com-inspired but constrained:
  - Linear connected steps only
  - Palette for Email, Wait, LinkedIn Task, and General Task
  - Canvas for nodes
  - Inspector for selected-step configuration
  - No branching, filters, webhooks, or arbitrary external IO in MVP
- Sequence permissions are simple for MVP:
  - All workspace users can view sequences
  - All workspace users can create, edit, and publish sequences
  - Users enroll people with their own connected Gmail sender
  - Users can pause and resume their own enrollments
  - No custom sequence role model in MVP
- Published sequences use version snapshots.
  - Existing enrollments remain on their starting version.
  - New enrollments use the latest published version.
- Archive and delete rules:
  - Archive is allowed for published or draft sequences.
  - Delete is allowed only for drafts with no enrollments/events.
  - Published sequences with history must be archived, not deleted.
- Email steps:
  - User defines a per-step prompt.
  - User generates and saves one final subject/body per email step.
  - Saved content is sent to every enrolled person who reaches that step.
  - No per-recipient email personalization for MVP.
- LinkedIn task steps:
  - No LinkedIn connection in MVP.
  - Generate per-person task copy with Groq when the task becomes due.
  - Task text is editable before completion.
- General task steps:
  - Create dashboard tasks when due.
  - Task completion lets the enrollment continue.
- Wait steps:
  - Use calendar days.
  - After the target calendar date, execution waits for the next valid sending window when the next executable step is an email.
- Sending windows:
  - Default weekdays, 9:00-17:00.
  - Use sender or workspace timezone.
  - First email also waits for the next valid window.
- Send limits:
  - Default 50 emails per day per connected Gmail account.
  - Default 10 emails per hour per connected Gmail account.
  - When limits are hit, send FIFO by due time.
- Gmail integration:
  - Separate Gmail connection from normal Google login.
  - Store connection status, granted scopes, token expiry, and sync metadata.
  - Encrypt access and refresh tokens at rest.
  - Disconnect action deletes/revokes the integration and pauses affected autosend.
  - Use Gmail send access for autosend.
  - Use Gmail metadata access for reply detection in test environment; production verification comes later.
- Reply detection:
  - Store Gmail thread IDs for sent emails.
  - Detect replies by metadata/thread activity.
  - Do not read reply bodies in MVP.
  - Stop only the specific enrollment that owns the replied thread.
- Worker:
  - Separate process from the API server.
  - Polls every 60 seconds.
  - Claims due work idempotently.
  - Enforces sending windows and send limits.
  - Retries transient Gmail failures with limited backoff.
  - Creates reconnect warnings for token/scope/revocation failures.
  - Blocks invalid recipient, missing email, and suppressed-recipient sends without retry.
  - Creates dashboard tasks for failures needing human action.
- Live-send gate:
  - Real worker path is built, but live Gmail sending is disabled by default.
  - When disabled, the worker records "would send" activity instead of calling Gmail.
  - Live sending is enabled explicitly by environment configuration.
- Groq:
  - Used for email-step content generation during sequence editing.
  - Used for LinkedIn/manual task text generation when those tasks become due.
  - Failures block the affected enrollment and create dashboard work rather than sending fallback copy.
- Dashboard:
  - Show due manual tasks.
  - Show failed sequence steps.
  - Show Gmail connection warnings.
  - Show recent sequence activity.
  - Show counters for active enrollments, emails sent today, replies detected, and failed steps.
- Unsubscribe:
  - Every autosent email includes a public token unsubscribe URL.
  - Unsubscribe page lives in the web app.
  - API owns token preview, confirmation, and suppression writes.
  - Suppression is workspace-level by recipient email.
  - Suppressed emails block future sequence sends.
- Data retention:
  - Preserve sent/reply/unsubscribe/failure/task history for published sequences.
  - Hard delete only safe draft records with no operational history.
- Outbound routes and service contracts should be designed around public behavior: create/update/publish sequences, enroll people, connect Gmail, execute due work, detect replies, list dashboard work, and unsubscribe.
- Prefer deep modules with small interfaces for:
  - Sequence scheduling and step advancement
  - Gmail send and reply-detection adapter
  - Gmail token encryption and refresh handling
  - Worker due-work claiming and execution
  - Send-window and rate-limit enforcement
  - Suppression/unsubscribe handling
  - Groq generation boundary
  - Sequence activity/event recording

## Testing Decisions

- Use TDD with vertical tracer bullets:
  - Write one behavior test.
  - Watch it fail.
  - Add the smallest implementation that makes it pass.
  - Repeat for the next behavior.
- Tests should verify public behavior, not private implementation details.
- Mock only system boundaries:
  - Gmail API
  - Groq API
  - Time/clock
  - Live-send environment gate
- Do not mock internal sequence modules merely to assert call order.
- API tests must stay under the API test directory.
- Web tests must stay under the web test directory.
- Preserve existing 100% coverage thresholds for configured DB-free coverage boundaries.
- Add/update tests whenever runtime code changes.
- Backend tracer bullet should come first:
  - Create draft sequence with Email, Wait, and LinkedIn Task steps.
  - Publish sequence.
  - Enroll one person.
  - Run worker with live sending disabled.
  - Verify observable activity shows a due email would be sent without calling Gmail.
- Additional API behavior tests should cover:
  - Sequence creation validation
  - Publishing and version snapshot behavior
  - Enrollment from existing people
  - People without email addresses
  - Sending-window scheduling
  - Per-account rate limit blocking
  - Suppression blocking future sends
  - Public unsubscribe preview and confirmation
  - Reply detection stopping only the owning enrollment
  - Pause/resume at sequence and enrollment levels
  - Transient Gmail retry behavior
  - Non-retry Gmail failure behavior
  - Groq failure blocking autosend and creating dashboard work
  - Archive/delete guardrails
- Additional web behavior tests should cover:
  - Sequences route rendering
  - Builder adding/configuring supported linear step types
  - Sequence list status display
  - Sequence detail tabs
  - People bulk enrollment action
  - Gmail connection state UI
  - Dashboard task/failure/warning sections
  - Public unsubscribe confirmation page states
- Existing prior art:
  - API route and middleware tests already exercise public route behavior.
  - Web service tests already cover service-layer contracts.
  - Shared test setup already separates API and web test suites.

## Out of Scope

- Full Make.com clone behavior.
- Branching, routers, filters, conditions, or A/B tests.
- Arbitrary external IO blocks or webhooks.
- LinkedIn account connection or LinkedIn autosend.
- Email open tracking.
- Email click tracking.
- Per-recipient email personalization for autosent email steps.
- Workspace-level brand voice settings.
- Reading reply bodies.
- AI reply summaries or sentiment analysis.
- CSV import directly into sequence enrollment, unless separately added to the People module.
- Custom sequence permissions beyond the simple workspace-member rules.
- Step-level pause/resume.
- Production Google OAuth verification work, although the implementation should be designed with verification and restricted/sensitive scope review in mind.

## Further Notes

- Google treats Gmail send and metadata/read-related access as sensitive or restricted depending on scope. The MVP can be developed in test mode, but production rollout needs verification planning and clear user-facing consent.
- The FTC CAN-SPAM guidance requires commercial email to include a clear opt-out mechanism and to honor opt-outs promptly. The suppression system is a core product requirement, not a later enhancement.
- Autosend is powerful enough to damage sender reputation or recipient trust if built loosely. Conservative defaults, visible failure states, idempotent worker execution, and live-send gating are required from the first implementation.
- The first implementation should start with backend behavior before the visual builder. The UI should wire into proven sequence/enrollment/worker contracts rather than defining behavior only on the client.
